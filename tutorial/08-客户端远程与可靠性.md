## 8.1 界面上的三种文字

点发送设 `loading = true`，收到文字设回 `false`？对 Agent 不行：模型可能先说一段，再调工具，再继续说。

| 数据 | 谁改 | 用途 |
| --- | --- | --- |
| 草稿 | 用户 | 还没提交的输入 |
| 流式预览 | `text.delta` 事件 | 尽早看到输出 |
| 正式消息 | `message` 事件 | 这一轮确定下来的文字 |

正式消息到了，要**替换**预览，而不是再追加一份。`message` 事件**不代表**运行结束，只有 `run.end` 才把“忙碌”清掉。所以“正式消息已到，界面仍显示忙碌”可以是正确的：Agent 接下来还要调工具。

还有两个细节：

- **切换会话的迟到响应**：打开 A → 切到 B → 切回 A，第一次 A 的请求这时才回来。sessionId 没错，但它属于上一次打开。用递增的 `generation` 区分，和 Versta 第 8 章一样。
- **审批面板防误触**：面板弹出时，用户刚才发消息按的 Enter 可能还在输入队列里。Hikaro 的面板忽略最初的 Enter，“允许”需要导航过或等待一小段时间，“拒绝”不用等。

## 8.2 JSONL 协议：一行一条消息

Hikaro 的界面（或 Pi 扩展、远程宿主）和 Agent 宿主进程之间，用 `--rpc` 模式通信：stdin/stdout 上**一行一个 JSON**（JSON Lines）。

```ts
// 源码：packages/protocol/src/index.ts（JsonLines）
export class JsonLines {
  private buffer = "";
  private decoder = new TextDecoder("utf-8", { fatal: true });
  constructor(private receive: (message: unknown) => void, readonly maxBytes = 1_048_576) {}
  push(chunk: Uint8Array) {
    this.buffer += this.decoder.decode(chunk, { stream: true });
    let index: number;
    while ((index = this.buffer.indexOf("\n")) >= 0) {
      const line = this.buffer.slice(0, index).replace(/\r$/, "");
      this.buffer = this.buffer.slice(index + 1);
      if (Buffer.byteLength(line) > this.maxBytes) throw Error("Protocol frame too large");
      if (line) this.receive(JSON.parse(line));
    }
    if (Buffer.byteLength(this.buffer) > this.maxBytes) throw Error("Protocol frame too large");
  }
}
```

这是本课程第四次看到“攒缓冲、找分隔符、切出一条”（SSE、Versta 的 JSON-RPC、LSP、这里）。再加上：

- `{ stream: true }`：汉字被切开也不乱码；`fatal: true`：非法 UTF-8 直接报错。
- **单帧上限 1 MiB**：缓冲区再长也不等了，防止内存被撑爆。
- 解析出来是 `unknown`，再用 Zod 的 `Command.parse` 检查 `id`、`scope`、`method`、`params`。JSON 语法对，不代表命令合法。

三个“编号”别混：

| 字段 | 回答 |
| --- | --- |
| 请求 `id` | 这个响应对应哪个请求 |
| `scope` | 属于哪个客户端（哪个窗口/设备） |
| 事件 `seq` | 持久化事件读到哪了（可跳号） |

**受理 ≠ 完成。** `prompt` 返回 `accepted` 只表示进了处理流程；完成要看后续的 `run.end` 事件。

## 8.3 停止按钮不能排队

普通命令按 scope 排队，一个个执行。但如果“审批回复”也排在队里：

```text
任务 A：等审批回来才能结束
审批回复：等任务 A 结束才轮到我
```

互相等待，谁也走不动。这就是**死锁**，单线程照样会发生。

解决：区分**工作命令**和**控制命令**。控制命令（`cancel`、`approval.respond`、`steer`、`client.detach`、`command.receipt` 等）不排队，直接处理：

```ts
// 示例：结构示意
if (isControlMethod(method)) return handle();   // 控制命令：立即处理
return previous.then(handle);                   // 工作命令：排队
```

控制通道只是**不排队**，不是“免检查”：身份、参数、审批归属照样要验。

还有两个“结束”别混：**断开视图**（`client.detach`）不等于**停止工作**。用户关掉窗口，后台任务可以继续；但撤销设备时，要能找到它留下的后台工作并取消。

## 8.4 接入 Pi：先说清谁在执行

Hikaro 和 Pi（另一个 Agent）有三种组合，名字里都有 Pi，执行者却不同：

| 用法 | 界面 | 谁跑 Agent 循环 |
| --- | --- | --- |
| Hikaro 原生，用 pi-ai 模型库 | Hikaro | Hikaro |
| `--backend pi` | Hikaro | 外部 Pi 进程 |
| Pi 扩展里打开 `/hikaro` | Pi | Hikaro（`--rpc` 宿主） |

权限、历史、停止语义都跟着**实际执行者**走。Hikaro 规定：启动失败时**不许悄悄换另一个执行者**，否则用户选的权限和模型就变了，界面却像什么都没发生。

`--backend pi` 的适配器要把 Pi 的事件翻译成 Hikaro 事件，而且只有“已受理”和“已结算”两个事件**都到了**才算完成（它们可能以任意顺序到达）。停止时要先清 Pi 的队列，再中止当前任务，否则排队的提示会接着跑。

## 8.8 断线重连：结果未知时别换 id 重发

请求超时，客户端看到的都一样，但宿主那边可能是：

- 请求没到；
- 到了，还在跑；
- 跑完了，响应丢了。

所以客户端的报错写的是 `Request timed out; command outcome may be unknown`，重连后**不会自动重发**。

Hikaro 的命令回执（`rpc_commands` 表）和 Versta 的发送回执是同一个思路：

```js
// 源码：packages/storage/src/worker.mjs（acceptCommand，节选）
db.exec("BEGIN IMMEDIATE");
const receipt = handlers.commandReceipt(args);
if (receipt) {
  if (receipt.digest !== null && (receipt.digest !== digest || receipt.method !== method))
    throw Error("Command ID payload conflict");   // 同 id 不同内容：冲突
  db.exec("COMMIT");
  return { inserted: false, receipt };            // 同 id 同内容：返回已有回执
}
// …插入新回执，状态 'accepted'
```

- 每条命令存 `digest`（内容摘要）。同 id 同内容 → 返回原回执；同 id 不同内容 → 报冲突。
- 查回执时，如果状态是 `accepted`，但记录它的是**另一个宿主实例**（`hostInstanceId` 不同，说明宿主重启过），就报告 `unknown`：之前那个实例可能做了一半。
- 客户端可以用控制命令 `command.receipt` 只读地查询。

正确的恢复顺序：**重连 → 查回执 → 查现场 → 必要时由用户决定重发（用原 id）**。用新 id 重发，可能制造第二次副作用。

心跳通了也只说明**连接**活着，不说明 Agent 在前进，更不说明任务做对了。

## 8.9 先写“不能发生什么”

“稳定、安全、可靠”没法直接测。先写成**不变量**：任何合法路径下都不能被破坏的条件。

| 不变量 | 观察什么 |
| --- | --- |
| 审批拒绝，不产生副作用 | 写入/启动次数 = 0 |
| 取消后，不再开始新工具 | 没有新的 `tool.start` |
| 清理没完成，不报告“已取消” | 清理闸门没开时，主 Promise 未结束 |
| 回执丢了，不自动再执行 | 副作用次数不增加 |

## 8.10 用闸门安排时序，测试要能失败

正常跑一遍通常避开了最危险的时间窗口。要测竞态，就**自己控制**什么时候发生什么：

```js
// 示例
await started.promise;        // 等被测代码真的走到检查点，而不是 sleep 猜
requestCancel();
assert.equal(finished, false);
cleanupGate.resolve();        // 测试决定什么时候放行清理
await work;
```

测试本身可能骗人。一个真实例子（来自 Hikaro 旧版加密测试，结构如下）：

```js
// 示例：复现同样的调用结构
let calls = 0;
function receive() { calls++; throw Error("auth failed"); }
function hello() { throw Error("already started"); }
assert.throws(() => receive(hello()));   // 通过了！
assert.equal(calls, 0);                   // 但 receive 根本没被调用
```

JavaScript 先计算参数，`hello()` 先抛了错，`receive` 没执行。宽泛的 `toThrow` 照样通过，测的根本不是“错误身份被拒绝”。

更可靠的写法：

- 在断言外准备好有效输入，先做一次正向对照；
- 只把目标调用放进错误断言，并检查具体错误原因；
- 拒绝类测试还要断言副作用为 0；
- **删掉被测的保护代码，确认测试会失败**，再恢复。

## 8.11 测量：别用一个数字代替所有事实

一次运行至少分开三件事：

| 维度 | 例子 |
| --- | --- |
| 执行状态 | completed / failed / unknown |
| 业务验收 | 修改符合约束吗？独立检查通过了吗？ |
| 资源 | 时长、调用次数、成本 |

`run.end = completed` 只说明循环正常结束；模型说“测试通过”也不是验收。成功应定义为“completed **且** 独立检查通过”。

**缺失的成本不能当 0。** 有的 Provider 不报告成本，用 `null` 表示“没观测到”，和明确报告的 `0` 分开统计，否则平均成本好看得很假。

p95 延迟要说明算法和样本数。只有 10 个样本，p95 基本就是最大值。
