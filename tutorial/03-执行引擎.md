## 3.1 三个词：Session、Run、Turn

| 词 | 意思 | 例子 |
| --- | --- | --- |
| **Session**（会话） | 一段持续的对话，保存全部历史 | 你一直在讨论这个项目的那个对话 |
| **Run**（一次运行） | 处理一条用户输入的完整过程 | “修复空字符串的 bug” |
| **Turn**（一轮） | Run 里的一次“请求模型 + 执行工具” | 模型要求读文件，程序读完存好结果 |

一个 Session 有很多 Run，一个 Run 有很多 Turn（第 1 章循环的每一圈）。

**模型返回了 ≠ Run 结束了。** 它可能只是在说下一步要做什么。

## 3.2 本章要守住的三条规则

1. **同一个 Agent 上，Run 不重叠。** A 没结束，B 只能等。
2. **每个调用者最终都能拿到自己那条输入的结果**（完成或失败），而不是只拿到“已入队”。
3. **取消后仍要收尾。** 发出停止信号，不代表马上可以开始下一个。

## 3.3 排队：一个队列 + 一个消费者

```js
// 示例
const a = agent.prompt("任务 A");
const b = agent.prompt("任务 B");
```

两次调用之间没有 `await`，如果 `prompt()` 里直接开始执行，A 和 B 就会交错：两个循环同时往一份历史里写消息。**JavaScript 单线程不会帮你排队**，每个 `await` 都让别的代码有机会插进来。顺序要自己安排。

Hikaro 的做法：`prompt()` 只负责入队，`drain()` 负责一个个取出执行。

```ts
// 源码：packages/core/src/index.ts（prompt/enqueuePrompt，简化）
let resolve, reject;
const completion = new Promise<void>((yes, no) => { resolve = yes; reject = no; });
if (this.queue.length >= 32) throw Error("Prompt queue is full");
this.queue.push({ id: randomUUID(), text, images, origin, resolve, reject });
void this.drain();
return completion;
```

队列项里存着 `resolve` 和 `reject`：这是**通知这个调用者最终结果的出口**。调用者 `await` 的是 `completion`，等到的是“我这条执行完了”，而不是“我这条入队了”。

```ts
// 源码：packages/core/src/index.ts（drain，去掉持久化和取消代数后的骨架）
if (this.draining) return;   // 已经有消费者在干活了
this.draining = true;        // 先占位，再 await
try {
  while (this.queue.length) {
    const item = this.queue.shift()!;
    try {
      await this.run(item.text, item.images);
      item.resolve();
    } catch (e) {
      item.reject(e);
    }
  }
} finally {
  this.draining = false;
}
```

关键顺序：**先把 `draining` 设为 true，再 `await`。** 如果把占位放在某个 `await` 之后，等待期间第二次调用 `drain()` 会以为“没人在干活”，就出现两个消费者。

内层 `catch` 只让当前这一项失败，循环继续处理下一项。A 失败了 B 照样执行；如果 B 依赖 A，得另定策略。

（真实代码还会把队列项写进数据库 `pendingStore`，这样程序崩溃重启后能知道有哪些消息还没处理，第 6 章讲。）

## 3.4 插话（steer）：补充当前任务，而不是排下一个

A 正在修代码，你又输入“别改公共接口”。这句话的意图有两种：

| 意图 | 用什么 | 什么时候生效 |
| --- | --- | --- |
| A 做完再做这个 | `prompt()` | 下一个 Run |
| 告诉正在做 A 的 Agent | `steer()` | 当前 Run 的下一轮 |

`steer()` 把文字放进另一个队列（上限 16 条）。`run()` 每一轮请求模型前调用 `applySteering()`，把攒下的补充指令全部取出，作为 user 消息追加到历史：

```ts
// 源码：packages/core/src/index.ts（run 循环里，每轮开头）
await this.applySteering(signal);
const { system, tools, context } = await this.requestContext(user.seq, signal);
```

**插话不是抢占。** 已经发出去的模型请求不会被改，正在执行的工具不会被打断。补充指令要等循环走到下一轮开头才被看到。

另外，Run 准备正常结束时也会检查：如果这时有新的插话，就再跑一轮，而不是带着没读的指令结束。

## 3.5 取消：排队的和正在跑的，处理方式不同

```ts
// 源码：packages/core/src/index.ts
cancel(preserveRecovered = false) {
  this.cancelEpoch++;
  this.controller?.abort();
  void this.discardPending(/* … */);
  this.discardSteering(/* … */);
}
```

- **排队中的**：还没开始，直接丢掉并 `reject`。
- **正在跑的**：只能通过 `controller.abort()` 发出信号，让执行链自己停下来。
- **插话**：一起清掉，别留给下一个任务。
- `cancelEpoch++`：取消“代数”加一。`drain()` 取出一项后会比较代数，发现取出前发生过取消就不执行，堵住“取消和出队同时发生”的缝。

注意 `cancel()` **没有**把 `draining` 设成 false。旧的 Run 还没退场，不能宣布“空闲了”。

### AbortSignal 是通知，不是撤销按钮

`AbortController.abort()` 只是把 `signal.aborted` 设为 true，并通知监听者。下游代码必须**自己检查或监听**它才会停：

```ts
// 示例
async function acceptResult(work, signal) {
  signal.throwIfAborted();          // 开始前：已取消就别开始
  const result = await work();
  signal.throwIfAborted();          // 回来后：取消期间回来的结果不接受
  return result;
}
```

Hikaro 在 `run()` 里到处是 `signal.throwIfAborted()`：每轮开头、模型流结束后、执行工具前。模型流结束后的那次检查尤其重要：用户取消后，模型可能仍然把完整回复送了回来，这个**迟到的成功**不能写进历史。

但**结果不被接受，不等于动作没发生。** 工具可能在你点取消前已经改了文件。取消只阻止“继续”，不负责“撤销”。

## 3.6 预算：循环必须有上限

模型可能一直要求调用工具，永远不说“完成”。不能指望模型自己克制，宿主要设硬上限：

| 限制 | 默认值 | 管什么 |
| --- | --- | --- |
| `maxTurns` | 32 | 一个 Run 最多几轮 |
| `modelCallsLeft` | 128 | 剩余模型调用次数（子 Agent 共享） |
| `maxCost` | 10 | 累计成本阈值（按 Provider 报告的 cost） |

```ts
// 源码：packages/core/src/index.ts（run 循环，请求模型前）
if (this.usage.cost >= this.budget.maxCost) throw Error("Session cost budget reached");
if (this.budget.modelCallsLeft <= 0) throw Error("Shared model-call budget exhausted");
this.budget.modelCallsLeft--;
```

两个细节：

- **先检查再扣减，紧挨着请求。** 子 Agent 共享同一个预算对象（第 7 章）。如果检查和扣减之间隔着 `await`，两个 Agent 可能同时看到“还剩 1 次”，然后都去用。代码注释特意写了：最后一次 await 之后再检查，保证只有一个请求能拿到最后一个名额。
- **成本阈值可能被越过。** 成本是请求**结束后**才知道的。已用 0.8、阈值 1.0，下一次请求照样能发；它报告 0.35，累计 1.15，再下一次才被拒绝。这个检查能阻止**继续**花钱，不能保证总账单不超过阈值。

## 3.7 错误分三类

| 情况 | 怎么处理 |
| --- | --- |
| 工具失败（找不到文本、参数错） | `isError: true` 结果写回历史，模型自己调整，循环继续 |
| 轮数/预算用完、模型响应不完整 | 本次 Run 失败，抛错 |
| 已取消 | 不接受迟到结果，以取消状态收尾 |

`run()` 的 `catch` 发出 `run.end` 事件，状态是 `cancelled` 或 `failed`；正常结束是 `completed`。

## 3.8 收尾：finally 和会话租约

同一个会话可能在两个终端窗口里打开。如果两边同时执行，就会同时往一份历史里写。所以 Run 开始前要拿到**会话租约**（lease）：数据库里一条“这个会话现在归我执行”的记录。

```ts
// 源码：packages/core/src/index.ts（ownLease，简化）
const lease = await this.options.store.acquireLease(sessionId, randomUUID());
if (!lease) throw Error("Session is running elsewhere");
const timer = setInterval(() => {
  // 每 10 秒续约；续约失败就 abort 当前 Run
  store.renewLease(sessionId, lease).then((ok) => { if (!ok) controller.abort(Error("Session lease lost")); });
}, 10000);
return async () => { clearInterval(timer); await store.releaseLease(sessionId, lease); };
```

**租约**和普通锁的区别：它有期限，持有者必须定期续约。持有者崩溃了不续约，租约过期，别人就能接手，不会永远卡住。反过来，续约失败（比如被别人接手了）就必须停下，这就是为什么 `signal` 被取消不一定是用户点了停止。

`run()` 的 `finally` 释放租约：

```ts
// 源码：packages/core/src/index.ts（run 结尾）
finally {
  try {
    await stopLease?.();
  } finally {
    this.controller = undefined;
  }
}
```

两层 `finally`：即使释放租约抛错，也要清掉 controller。但 `finally` 只保证**尝试**清理，不保证清理成功；进程被强杀时它根本不会执行。

node --test labs/03-runner.mjs

实验实现了一个小执行器：队列、单消费者、插话、取消、调用预算。

1. 为什么不能在 `queue.push()` 之后立刻 `resolve()`？
2. 把实验里 `drain()` 的 `this.draining = true` 挪到第一个 `await` 之后，哪个测试会失败？
3. 预算剩 1 次，两个子 Agent 几乎同时请求模型。如果检查和扣减之间有一次 `await`，会发生什么？

<details><summary>答案</summary>

1. 那样调用者以为任务完成了，实际才刚入队。调用者 `await` 的应该是执行结果。
2. “两个任务不重叠”那个测试：等待期间第二次 `drain()` 看到 `draining` 还是 false，就启动了第二个消费者。
3. 两个都通过检查，都扣减，实际用了 2 次，`modelCallsLeft` 变成 -1。

</details>
