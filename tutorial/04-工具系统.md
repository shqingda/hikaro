## 4.1 工具是一份契约

可以拿后端接口类比：

| 后端接口 | 工具 |
| --- | --- |
| 接口文档 | 名称 + 描述 + 参数 JSON Schema |
| 路由表 | `ToolRegistry` |
| 请求体校验 | `schema.safeParse()` |
| handler | `execute()` |

一个好工具不只规定“参数长什么样”，还规定“操作承诺什么”。比如 `edit_file` 的契约：

- 接收**预期的旧文本**和新文本；
- 旧文本在文件里**必须恰好出现一次**，否则拒绝；
- 需要权限时先审批；
- 返回模型能看懂的结果。

“恰好一次”这种承诺，类型写不出来，要靠 `execute` 里的代码保证。描述里写了什么，代码就要真的做到什么。

```ts
// 源码：packages/core/src/types.ts（Tool 的主要字段）
type Tool = {
  name: string;
  description: string;
  schema: ZodType;            // 本机校验
  parameters?: Record<string, unknown>; // 可选：自己提供给模型的 JSON Schema
  deferred?: boolean;         // 暂不展示给模型（4.5）
  execute(args, context: ToolContext): Promise<ToolResult>;
};
```

## 4.2 注册表：先全部检查，再一起写入

注册一批工具时，如果其中有重名，应该怎么办？

```ts
// 源码：packages/core/src/index.ts（ToolRegistry.registerAll）
registerAll(tools: Tool[]) {
  const names = new Set<string>();
  for (const tool of tools) {
    if (this.tools.has(tool.name) || names.has(tool.name))
      throw Error(`Duplicate tool: ${tool.name}`);
    names.add(tool.name);
  }
  for (const tool of tools) this.tools.set(tool.name, tool);
}
```

两遍循环：**第一遍只检查**（和已有的重名？这批内部重名？），**第二遍才写入**。如果边查边写，查到第三个发现重名时，前两个已经写进去了，留下“半套工具”。

这是“全有或全无”的思路，和数据库事务一样，只不过这里是一个同步函数、一个内存 Map。

## 4.3 运行时校验：类型骗不了网络

你在 TypeScript 里写了 `{ path: string }`，模型照样可能发来 `{ path: 123 }`。TypeScript 类型在编译后就消失了，**运行时不检查任何东西**。

所以 `invoke()` 必须真正校验（第 1 章见过）：

```ts
// 源码：packages/core/src/index.ts（Agent.invoke）
const parsed = tool.schema.safeParse(args);
if (!parsed.success)
  return { text: `Invalid arguments: ${parsed.error.message}`, isError: true };
// 后面执行的是 parsed.data，不是 args
```

校验不只是“通过/不通过”，还会**补默认值**：

| 模型发来 | `read_file` 校验后 | 能执行吗 |
| --- | --- | --- |
| `{ path: "a.ts" }` | `{ path: "a.ts", offset: 1, limit: 200 }` | 进入下一步（权限） |
| `{ path: "a.ts", limit: 0 }` | 失败（`min(1)`） | 不执行 |
| `{ path: 123 }` | 失败 | 不执行 |

所以校验完必须用 `parsed.data`。用回原始 `args`，默认值就丢了。

一个 Zod schema 服务两个方向：本机用它校验；`z.toJSONSchema()` 把它转成 JSON Schema 发给模型。不是所有 Zod 功能都能转成 JSON Schema（比如自定义转换函数），用到时要分别测试“模型看到的定义”和“本机实际接受的输入”。

**测试要测副作用。** 只断言“返回了 `isError: true`”不够，还要断言 `execute` 一次都没被调用、文件没变。

## 4.4 ToolContext：宿主提供的环境

工具需要知道：当前工作目录？哪个会话？用户取消了吗？怎么请求审批？这些**不能让模型通过参数传**，否则模型可以自己填“已批准”。

所以由 `invoke()` 构造一个 `ToolContext` 交给工具：

```ts
// 源码：packages/core/src/index.ts（invoke 内构造 context，节选）
const context: ToolContext = {
  checkpoint: () => this.checkExecution(signal),  // 检查：没取消？租约还在？
  cwd: this.options.session.cwd,
  sessionId: this.options.session.id,
  signal,
  callId,
  budget: this.budget,
  approve: async (reason, capability) => {
    await this.checkExecution(signal);    // 等审批前检查
    const approved = await this.options.approve({ /* … */ });
    // …等审批后再检查一次
  },
  // invoke：工具调用工具，见 4.6
};
```

类比后端：请求体是业务数据（模型参数），服务端上下文是认证身份（ToolContext）。

## 4.5 等待之后，再检查一次

审批要等用户点按钮，可能等好几分钟：

| 时刻 | 发生什么 |
| --- | --- |
| A | 工具请求审批 |
| B | 用户取消了整个任务 |
| C | 审批结果终于返回“允许” |
| D | 工具准备写文件 |

只在 A 检查取消，就会在 D 写入一个已经被取消的任务。所以 `ctx.approve()` 在等待**前后**都调用 `checkExecution()`；工具在真正写入前还应调用 `ctx.checkpoint()`：

```ts
// 示例：一个文件修改工具的关键顺序
if (!(await ctx.approve("Replace greeting"))) throw Error("Permission denied");
await ctx.checkpoint();     // 等完审批，再确认没取消、租约还在
// 再检查预期旧内容，然后写入
```

这是第 3 章“await 之后重新检查”的又一次应用。

注意：这是**协作约定**。工具得自己调用这些检查。随便一段第三方代码跑在同一个 Node 进程里，不会因为拿到 context 就被约束；真正的隔离要靠沙箱（第 5 章）。

## 4.6 工具调用工具：走同一个入口

有的工具内部还要调用别的工具（比如“读取并分析”调用 `read_file`）。Hikaro 让它通过 `ctx.invoke()` 回到同一个 `Agent.invoke()` 入口，于是：

- 同样经过工具查找、参数校验、权限检查，没有后门；
- 取消信号一路传下去；
- 嵌套层数 +1，超过 8 层直接报错（`Tool nesting limit exceeded`），防止无限递归；
- 记下 `parentCallId`，事件里能看出“谁调用了谁”。

## 4.7 工具多了：延迟展示

工具很多时，全部定义都塞给模型会占大量上下文，还会让模型选错。Hikaro 支持把工具标成 `deferred`：

```ts
// 源码：packages/core/src/index.ts（ToolRegistry）
definitions() {
  return [...this.tools.values()]
    .filter((t) => !t.deferred)
    .map((t) => ({ name: t.name, description: t.description, parameters: t.parameters ?? z.toJSONSchema(t.schema) }));
}
search(query: string) {
  const matches = [...this.tools.values()]
    .filter((t) => (t.name + " " + t.description).toLowerCase().includes(query.toLowerCase()))
    .slice(0, 12);
  for (const t of matches) t.deferred = false;   // 搜到的工具，之后都可见
  return this.definitions().filter((t) => matches.some((m) => m.name === t.name));
}
```

模型先通过一个搜索工具找到需要的工具，之后它的定义才进入请求。

**隐藏不是授权。** `get(name)` 照样能按名字找到 deferred 工具。要禁止某个工具，得靠权限策略，不能靠“不告诉模型”。

## 4.8 插件：注册失败要回滚

插件可以注册工具、命令、Provider、事件监听等。宿主先检查插件的 `apiVersion`，再调用它的 `setup()`。

如果 `setup()` 注册了工具 A、命令 B，然后抛错，Hikaro 会记下加载前的状态，把这次新增的注册项全部移除。

但回滚有边界：

```ts
// 示例：反例
await startExternalResource();  // 启动了一个外部进程
registerTool(tool);
throw Error("setup failed");
```

注册表回滚了，可外部进程还在跑。**谁创建资源，谁负责清理**：插件要在自己的失败路径里关掉已经启动的东西。

3. 为什么“工具已标成 deferred”不能当作“禁止使用”？

<details><summary>答案</summary>

1. 没有。第一遍检查就抛错了，第二遍写入根本没执行。
2. 不会。断言返回 `isError: true`，并且 `execute` 调用次数为 0（目标内容没变）。
3. `deferred` 只影响 `definitions()` 发给模型的列表，`get(name)` 照样找得到。模型猜中名字就能调用。
