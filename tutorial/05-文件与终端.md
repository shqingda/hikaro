## 5.1 cwd 是起点，不是围墙

模型传来 `path: "../../etc/passwd"`。`cwd`（当前工作目录）只是解析相对路径的起点，它不阻止 `../` 走出去。所以要单独判断“这个路径在不在工作区里”。

直觉写法 `path.startsWith(root)` 是错的：

```text
工作区：/work/app
目标：  /work/application/key.txt   ← 也以 /work/app 开头，但不在里面
```

正确做法是算相对路径，看它是否往外走：

```ts
// 源码：packages/tools/src/workspace.ts（resolvePath，节选）
const root = await realpath(cwd);
// …找到 path 的真实位置后：
const rel = relative(root, path);
return {
  path,
  inside: rel === "" || (!rel.startsWith("../") && rel !== ".." && !isAbsolute(rel)),
};
```

`relative('/work/app', '/work/application/key.txt')` 得到 `../application/key.txt`，以 `../` 开头，判定在外面。

## 5.2 符号链接：看起来在里面，其实在外面

**符号链接**（symlink）是一个指向别处的“快捷方式”。`/work/app/link.txt` 可能指向 `/Users/me/.ssh/id_rsa`。只看路径字符串，它在工作区里；真正读到的却是外面的文件。

所以先用 `realpath()` 解析出**真实路径**再判断。问题是：要新建的文件还不存在，`realpath` 会报 `ENOENT`。Hikaro 的处理是往上找到第一个**已存在的祖先目录**，解析它的真实路径，再拼回不存在的尾巴：

```ts
// 源码：packages/tools/src/workspace.ts（resolvePath 循环）
let ancestor = resolve(root, input);
const tails: string[] = [];
for (;;) {
  try {
    const path = resolve(await realpath(ancestor), ...tails.reverse());
    // …判断 inside（见上）
  } catch (e) {
    if (e.code !== "ENOENT") throw e;
    tails.push(basename(ancestor));
    ancestor = dirname(ancestor);
  }
}
```

三个概念别混：

| 概念 | 回答什么 |
| --- | --- |
| 原始路径字符串 | 模型想访问哪个名字 |
| 真实路径 | 检查那一刻实际指向哪里 |
| 允许访问 | 权限策略批准了吗 |

## 5.3 权限模式与“只读也有风险”

Hikaro 终端界面有三种权限模式：

| 模式 | 行为 |
| --- | --- |
| Ask（默认） | 工作区内编辑、沙箱内命令直接放行；越出工作区、不受限命令、MCP、浏览器操作要问 |
| Approve for me | 用保守的本地规则自动批准已知低风险操作 |
| Full Access | 文件工具可访问外部，命令在宿主上无沙箱、可联网运行 |

**只读也可能危险。** 读一个凭据文件再发给模型，信息就已经泄露了，不需要任何写入。所以敏感文件即使只读也要审批；搜索工具也不能绕过：搜索先列出命中的文件名，再逐个资源授权。

## 5.4 修改前，先确认没看错旧内容

一个普通的协作冲突：

| 时刻 | Agent | 你 |
| --- | --- | --- |
| 1 | 读到 `Helo, Ada!` | |
| 2 | 生成修改中… | 改成 `Helo, Lin!` |
| 3 | 写入 `Hello, Ada!` | 你的 `Lin` 没了 |

问题不在模型笨，而在程序没检查“修改依据还有效吗”。Hikaro 的两个写入工具各有前提：

```ts
// 源码：packages/tools/src/index.ts
// write_file：整文件替换，要求提供完整旧内容 expected
if (current !== undefined && expected !== current)
  throw Error("File changed or expected content missing. Read it before replacing.");

// edit_file：局部替换，要求旧文本恰好出现一次
const index = old.indexOf(oldText);
if (index < 0 || old.indexOf(oldText, index + 1) !== -1)
  throw Error("Expected exactly one match");
```

- `write_file`：“文件还是我读到的样子吗？”不是就拒绝。
- `edit_file`：“这段旧文本只有一处吗？”0 处或多处都拒绝，避免改错地方。从 `index + 1` 再找，连 `aaa` 里找 `aa` 这种重叠匹配也能发现。

这叫**乐观并发检查**：允许先准备修改，提交时再验证前提。冲突时正确的做法是报错让模型重新读，而不是自动用最新内容覆盖。

## 5.5 检查和使用之间的时间差

就算检查通过了，问题还没完：

```text
t1  检查 /work/docs/note.txt：在工作区内，允许
t2  另一个进程把 docs 换成了指向外部的符号链接
t3  按同一个字符串打开 note.txt → 打开的是外面的文件
```

这类漏洞叫 **TOCTOU**（Time Of Check to Time Of Use）：检查的时刻和使用的时刻，状态不一样了。

解决思路：**别按名字反复查找，而是一级级打开目录，拿到“句柄”后沿着句柄走。** 文件描述符（fd）是进程对一个已打开对象的引用；名字之后被换掉，已打开的 fd 仍指向原来的对象。

Hikaro 用一个小的 C 程序（`packages/tools/native/secure-file.c`）做实际文件操作：

```c
// 源码：packages/tools/native/secure-file.c（目录遍历，节选）
openat(parent_fd, component, O_RDONLY | O_DIRECTORY | O_NOFOLLOW | O_CLOEXEC);
```

- `openat(parent_fd, ...)`：相对**已打开的父目录**打开下一级，而不是重新从根解析整个路径；
- `O_NOFOLLOW`：这一级如果是符号链接，就拒绝；
- `O_DIRECTORY`：必须是目录；
- `O_CLOEXEC`：之后启动的子进程不会继承这个 fd。

### 写入：临时文件 + 原子替换

写到一半崩溃，文件就只剩半份。所以先写**临时文件**，写完、`fsync` 落盘，再用 `renameat()` 把它换到目标名字上。同一文件系统内，rename 是**原子**的：别人打开目标时，要么看到旧文件，要么看到新文件，不会看到半份。

宿主和 C 程序之间用简单的两阶段协议：先发 `PREPARE` 和新内容，C 程序准备好临时文件后回复；宿主**再检查一次**取消和租约，再发 `COMMIT`。

几层保护各管一件事：

| 机制 | 保护什么 | 管不到什么 |
| --- | --- | --- |
| 同路径队列（进程内） | 本进程对同一文件的修改不重叠 | 其他进程 |
| 锁文件 | 其他遵守协议的写入者 | 随便一个编辑器 |
| expected / 唯一匹配 | 修改依据没过时 | 禁止外部写入 |
| 原子替换 | 读者看不到半份文件 | 断电后一定持久 |

## 5.6 运行程序 ≠ 执行一段 shell

Agent 要跑测试，Node 用 `child_process.spawn()` 创建**子进程**：一个独立运行的程序，有自己的内存，通过管道和父进程交流。

两种启动方式差别很大：

```js
// 示例：直接运行程序，参数是数组
spawn("node", ["test.mjs", "hello; rm -rf ~"], { shell: false });
// → "hello; rm -rf ~" 只是一个普通参数字符串

// 示例：交给 shell 解释
spawn("/bin/zsh", ["-f", "-c", "npm test; echo done"]);
// → shell 解析分号、管道、重定向
```

Agent 的命令工具接收的是一段命令字符串，只能交给 shell 解释，所以危险性在 shell 这一层。Hikaro 的受限命令先启动沙箱运行器（`sandbox-runner.mjs`），在 macOS 沙箱里执行。

**环境变量也是输入。** 子进程默认继承父进程的环境变量，其中可能有 API key。Hikaro 的沙箱命令只保留 `PATH`、`HOME`、`TMPDIR`、`LANG`、`TERM` 等少数变量。

## 5.7 输出：有上限，还要一直读

程序通过 **stdout**（标准输出）和 **stderr**（标准错误）输出。和网络一样，`data` 事件给的是任意切分的块：不保证是整行，也可能把一个汉字切开，所以要设置 `utf8` 流式解码。

日志可能有几百 MB，不能全部塞给模型。Hikaro 的 `runProcess()`：

- **预览**：最多 48000 个字符，保留开头，超出标注截断，作为工具结果给模型；
- **归档**：配置了输出目录时，完整日志存文件，上限 50 MiB。

坑：**不存了，也得继续读。** 预览满了就停止读取 stdout？子进程继续往管道里写，管道缓冲区（操作系统给的一小块内存）满了以后，子进程的写操作会卡住，程序就永远不结束了。

写日志文件时还有**背压**：`writer.write()` 返回 `false` 表示“写不过来了，先别给我”。正确做法是暂停读取子进程输出，等 `drain` 事件再恢复，而不是无限往内存里堆。

## 5.8 停止：kill 是发信号，不是确认结束

`child.kill()` 只是**发送一个信号**。进程可以处理甚至忽略 `SIGTERM`；`SIGKILL` 无法忽略，但发出后也要等着确认它真的退了。

而且只杀 shell 不够：

```text
Hikaro
└── shell
    └── 测试程序
        └── 测试启动的子进程
```

Hikaro 在非 Windows 上用 `detached` 让子进程自成一个**进程组**，停止时对整组发信号：

```ts
// 源码：packages/tools/src/process-group.ts（stop）
this.signal("SIGTERM");
if (!(await wait(1000))) {          // 每 25ms 查一次，最多等 1 秒
  this.signal("SIGKILL");
  if (!(await wait(2000)))
    throw Error("Process group termination could not be confirmed; retry stop");
}
```

确认不了就报错，**不假装成功**。（主动脱离进程组的后代管不到；Windows 只能信号直接子进程，代码会明确报错说明。）

几个时间点别混：

| 事件 | 说明什么 |
| --- | --- |
| 发出 SIGTERM | 只是请求停止 |
| `exit` | 直接子进程退出了 |
| `close` | 它的 stdio 管道也关了，但后代可能还活着 |
| 进程组确认停止 | 整组都没了 |

超时让 Promise 返回 ≠ 进程停了。

## 5.9 交互终端：另一套生命周期

`npm run dev` 这种长期运行、可能需要输入的命令，不能“等它结束再返回”。Hikaro 提供一组工具：`terminal_start` 返回一个 ID，之后用 `terminal_read` 读输出、`terminal_send` 发输入、`terminal_stop` 停止。

它用 **PTY**（伪终端）运行程序，让程序以为自己连着一个真终端（支持颜色、光标控制、窗口尺寸）。PTY 只是交互方式，**不是安全隔离**。

两个规则：

```ts
// 源码：packages/tools/src/terminal.ts
const term = terminals.get(id);
if (!term || term.owner !== ctx.sessionId)
  throw Error("Terminal not found in this session");
```

- **终端属于会话。** 知道别的会话的终端 ID 也不能操作它。
- **`terminal_read` 是“取走”**：读完就清空缓冲。连续读两次，第二次可能是空的。

`terminal_stop` 返回只代表“已请求停止”；一次 Run 结束了，它启动的终端也不会自动关，需要显式停止。

## 5.10 沙箱和审批是两回事

- **审批**：决定这个操作**允不允许**。
- **沙箱**：限制程序**实际能碰到**哪些文件、能不能联网。

Hikaro 的工作区沙箱目前只支持 macOS：只能写工作区、不能联网。沙箱启动失败会直接报错，不会悄悄换成无限制运行。Full Access 是扩大权限，不是“兼容性更好的选项”。
