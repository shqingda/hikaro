## 2.1 一次模型请求里有什么

发给模型的不只是用户那句话，而是：

| 部分 | 内容 |
| --- | --- |
| system | 系统指令：你是谁、规则是什么 |
| messages | 第 1 章的整份历史 |
| tools | 工具定义（名称、描述、参数 JSON Schema） |

模型按 **token** 计量。token 是模型切分文本的单位，大致是一个英文单词的一部分或一两个汉字，不等于字符数，更不等于字节数。

两个容易混的上限：

- **上下文窗口**：一次请求里输入 + 输出最多多少 token。
- **输出上限**：这次最多生成多少 token。

输入越长，留给输出的空间越少。历史太长塞不进窗口，就要压缩（第 6 章）。

## 2.2 为什么要流式

模型生成一段长回答要好几秒。如果等全部生成完再显示，用户会盯着空白。所以模型服务一边生成一边发送，程序收到一点显示一点，这叫**流式**。

## 2.3 从 Promise 到 AsyncIterable

`Promise` 表示**一个**将来的结果。流式响应是**一连串**将来的结果，要用 **AsyncIterable**（异步可迭代对象）表示，用 `for await` 逐个取：

```js
// 示例
async function* fakeStream() {    // async function*：异步生成器
  yield { type: "text", text: "你" };
  yield { type: "text", text: "好" };
  yield { type: "done" };
}

for await (const event of fakeStream()) {
  console.log(event);
}
```

`async function*` 的星号表示“生成器”：函数可以多次 `yield` 交出值，每次交出后暂停，等消费者要下一个时再继续。`for await` 每取一个都会等它准备好。

Hikaro 的 Provider 接口就是这样定义的：

```ts
// 源码：packages/core/src/types.ts
export type ProviderEvent =
  | { type: "text"; text: string }        // 一段文字增量
  | { type: "thinking"; text: string }    // 一段推理过程增量
  | { type: "done"; message: Message; usage: Usage };  // 完整消息 + 用量

export interface ProviderAdapter {
  id: string;
  model: string;
  contextWindow: number;
  stream(input: {
    system: string;
    messages: Message[];
    tools: ToolDefinition[];
    signal: AbortSignal;
    sessionId?: string;
  }): AsyncIterable<ProviderEvent>;
}
```

**分工清楚**：`text` / `thinking` 增量只给界面显示用；`done` 里的完整 `message` 才写进历史、决定下一步。工具调用也只在 `done` 的 message 里，不在增量里。

## 2.4 网络交来的是字节，不是字

服务器通过 HTTP 发来的是**字节流**，每次到达多少字节由网络决定，和文字边界无关。

坑一：**一个汉字可能被切成两半。** UTF-8 编码里一个汉字占 3 字节。如果某次只到了前 2 个字节，直接解码就是乱码。正确做法是用流式解码器，把不完整的尾巴留到下次：

```js
// 示例
const decoder = new TextDecoder();
decoder.decode(chunk, { stream: true }); // stream: true → 不完整的字节先留着
```

坑二：**解码成功不等于能 `JSON.parse`。** 一段 JSON 也可能被切成两次到达。

## 2.5 SSE：一种“事件流”的格式

多数模型服务用 **SSE**（Server-Sent Events）格式传流式数据。它是纯文本，每个事件以空行结束：

```text
data: {"type":"text_delta","delta":"你"}

data: {"type":"text_delta","delta":"好"}

```

解析步骤：

```text
字节 → (流式解码) → 文本 → (按空行切) → 一个个事件 → (取 data 行) → JSON.parse → 模型协议事件
```

网络分块和事件边界**不对齐**：一块可能是半个事件，也可能是三个事件。所以要和 Versta 的 JSON Lines 一样，攒缓冲区，见到完整分隔符才切出一个事件，剩下的留着。

还要注意：SSE 只是“外层包装”，里面 `data` 的 JSON 结构是各家模型协议自己定的。OpenAI、Anthropic 等各不相同，所以下一层需要适配器。

## 2.6 工具参数也是一点点来的

模型调用工具时，参数 JSON 也可能分好几段流式到达：

```text
{"pa
th":"greet
ing.txt"}
```

**不能看到一个 `}` 就以为参数齐了**：字符串内容里也可能有 `}`。正确做法是等协议明确说“这个工具调用结束了”，再整体解析。

同一个回复里有多个工具调用时，它们的片段可能**交错到达**，所以要按调用编号（index 或 id）分别累积，不能用一个字符串变量拼。

Hikaro 不自己处理这些：它用 Pi 模型库，库负责拼好；Hikaro 只在 `done` 时拿完整的工具调用。

## 2.7 适配器第一步：把内部消息转成厂商格式

`toPi()` 把 Hikaro 的 `Message` 转成 Pi 库的消息：

```ts
// 源码：packages/provider-pi/src/index.ts（toPi，节选）
if (message.role === "tool")
  return {
    role: "toolResult",
    toolCallId: message.callId!,
    toolName: message.name!,
    content: [{ type: "text", text: message.text }, /* 图片… */],
    isError: message.isError ?? false,
    timestamp: message.timestamp,
  };
if (message.providerData) return message.providerData as AssistantMessage;
return {
  role: "assistant",
  content: [
    ...(message.text ? [{ type: "text", text: message.text }] : []),
    ...(message.toolCalls ?? []).map((t) => ({ type: "toolCall", ...t })),
  ],
  // …model、usage、stopReason: toolCalls 非空则 "toolUse"，否则 "stop"
};
```

三件事：

1. **角色名和字段名要换**：`tool` → `toolResult`，`callId` → `toolCallId`。
2. **assistant 消息优先用 `providerData`**：这是上次模型返回的原始消息，原样保存。有些厂商要求把它自己的原始格式（比如推理签名）原样送回，自己重建会丢信息。
3. **用户消息有两种形状**：纯文字时 `content` 是字符串；有图片时是数组。

## 2.8 适配器第二步：把厂商事件转成内部事件

反方向，把 Pi 的流式事件翻译成第 2.3 节的三种 `ProviderEvent`：

```ts
// 源码：packages/provider-pi/src/index.ts（stream 内，节选）
for await (const event of stream) {
  if (event.type === "text_delta") yield { type: "text", text: event.delta };
  else if (event.type === "thinking_delta") yield { type: "thinking", text: event.delta };
  else if (event.type === "error") throw Error(event.error.errorMessage ?? `Provider ${event.reason}`);
  else if (event.type === "done") {
    const m = event.message;
    yield {
      type: "done",
      message: {
        role: "assistant",
        text: m.content.filter((c) => c.type === "text").map((c) => c.text).join(""),
        toolCalls: m.content.filter((c) => c.type === "toolCall").map((c) => ({ id: c.id, name: c.name, arguments: c.arguments })),
        timestamp: m.timestamp,
        providerData: m,     // 原样留着，下次 toPi 用
      },
      usage: { input: m.usage.input, output: m.usage.output, cost: m.usage.cost.total },
    };
  }
}
```

`usage` 是厂商报告的用量和成本，第 3 章的预算检查靠它。

## 2.9 为什么这样分层好测

因为执行循环只依赖 `ProviderAdapter` 这个接口，测试时可以写一个**假 Provider**：按预设剧本 `yield` 事件，不联网、结果固定。第 1 章和第 3 章的实验都是这么做的。

## 练习

```bash
node --test labs/02-stream.mjs
```

实验实现了一个最小的 SSE 解析器：输入任意切分的字节块，输出事件。

1. “你好”的 UTF-8 字节被切成 `[e4 bd]` 和 `[a0 e5 a5 bd]` 两块。不用 `{ stream: true }` 逐块解码，会得到什么？
2. 为什么增量事件里不带工具调用，执行循环也能正常工作？
3. 为什么 `toPi()` 优先返回 `providerData`，而不是用 `text` 和 `toolCalls` 重新拼？

<details><summary>答案</summary>

1. 第一块解出替换字符（乱码），第二块开头也不完整，最终得不到“你好”。
2. 执行循环只根据 `done` 里的完整 message 决定下一步；增量只用于显示。
3. 厂商原始消息里可能有 Hikaro 内部格式表达不了的信息（如推理签名、特殊块），原样送回才不丢。

</details>
