## 6.1 三份不同的“历史”

聊天页面有 300 条消息，屏幕只渲染最近 20 条，没渲染的不代表删了。Agent 多了一层：**发给模型的消息，也是挑选过的。**

| 视图 | 在哪 | 用途 |
| --- | --- | --- |
| 持久化历史 | SQLite 事件表 | 全部事实，崩溃后能恢复 |
| 模型上下文 | 每次请求临时组装 | 装进上下文窗口的那部分 |
| 屏幕 | 界面内存 | 用户看到的 |

用户很早说过“只检查，不发布”。这条在数据库里有，屏幕上翻得到，但可能**已经不在模型上下文里**了。所以重要限制不能只靠一条很久以前的聊天记录维持，该用权限挡住的就用权限挡。

排查时别笼统说“Agent 忘了”，先分清是：没保存、保存了没发给模型、还是发了但没显示。

## 6.2 事件和投影

Hikaro 存的不是“消息数组”，而是**事件流**：`run.start`、`text.delta`、`message`、`tool.start`、`run.end`……每个事件一行，按递增的 `seq` 排序。

需要什么视图，就从事件里挑出来，这叫**投影**：

```ts
// 示例
const messages = events
  .filter((event) => event.type === "message")
  .map((event) => event.data.message);
```

模型历史只取 `message` 事件；界面还需要 `text.delta` 来显示正在生成的文字。同一批事实，不同用途。

## 6.3 装不下：按“整组”裁剪

上下文窗口有限，历史太长就得省略旧的。但不能随便删：

```text
U1 用户：检查文件
A1 模型：调用 read_file，id=r1
T1 工具：r1 的结果
A2 模型：结论
U2 用户：再看另一个文件
```

如果只留最后三条，T1 就失去了对应的调用 A1。很多模型 API 会直接拒绝这种“孤儿”工具结果。所以 Hikaro 的 `fitContext()` **只在 user 消息处切**，把一整段旧任务一起省掉：

```ts
// 源码：packages/core/src/context.ts（fitContext，节选）
const outputTokens = options.outputTokens ?? Math.min(16384, Math.max(256, Math.floor(contextWindow * 0.35)));
const safetyTokens = Math.ceil(contextWindow * 0.05);
const budget = contextWindow - outputTokens - safetyTokens;
// …算出 system、工具定义、每条消息的估计大小
for (let next = 1; next < messages.length && inputTokens() > budget; next++) {
  if (messages[next]!.role !== "user") continue;   // 只在 user 消息处切
  for (; start < next; start++) { /* 减去被省掉消息的大小 */ }
}
return { messages: messages.slice(start), overflow: inputTokens() > budget, /* … */ };
```

几个要点：

- **预算 = 窗口 − 留给输出的 − 5% 安全余量。** 输入要给输出留位置。
- **大小是估算，不是精确 token 数。** 精确计数需要每家模型的分词器；这里用基于 UTF-8 字节的保守估计（宁可高估）。注意 `"你".length` 是 1，但 UTF-8 是 3 字节，“长度”的单位要看清。
- **省略后插一条提示**：`Earlier conversation omitted … Do not assume its contents.` 告诉模型“前面有东西被省了，别瞎猜”。
- **切不下去就报 `overflow`**：当前这一轮自己就超了，只能报错让用户缩短输入或换更大窗口，不能假装装下了。

## 6.4 摘要：压缩，而不是删除

裁剪回答“这次不发什么”；**摘要**回答“把以前的事压缩成一段描述”。

Hikaro 在两种情况下自动摘要：已经开始省略旧消息，或者输入估算超过预算的 85%。流程：

1. 把旧历史分页读出来，交给模型（不给工具），要求保留目标、约束、已做动作、测试结果、待办、不确定点；
2. 得到摘要后存成一个**检查点**（checkpoint），记录“摘要覆盖到第几条（`throughSeq`）”；
3. 之后的请求 = 检查点摘要 + 检查点之后的消息。

**原始记录不删。** 摘要只是给模型看的压缩版。

好摘要要忠实：

```text
目标：定位登录失败原因；不发布。
已做：读了 auth.ts，第 30 行读取配置项 X。
未做：还没跑测试。
不确定：本地配置和线上是否一致。
```

“尚未测试”绝不能被压成“测试通过”。

如果摘要后还是装不下，或者摘要反而变大了，Hikaro 直接报错，**原历史保持不变**。手动 `/compact` 则会新建一个带 `parentId` 的子会话，把摘要作为新会话的起点。

## 6.5 SQLite：事件怎么存

```sql
-- 示例：按 Hikaro 的查询方式简化
SELECT seq, type, data FROM events
WHERE sessionId = ? AND seq > ?
ORDER BY seq LIMIT ?;
```

`seq` 是**全表**递增的，不是每个会话从 1 开始。会话 A 的事件号可能是 1、3、7。用“上次读到哪（游标）”分页：`seq > 上次的值`。别要求 `next === prev + 1`，跳号是正常的。

**事务**让一组写入要么全成、要么全不成。Hikaro 的关键一组是：**验证会话租约 + 追加事件**，放在同一个写事务里（`BEGIN IMMEDIATE`：一开始就拿写锁）。否则可能“刚验证完我还持有租约，还没写进去，租约就换人了”。

两个配置：

- `journal_mode=WAL`：写入先进日志，读者读自己的快照，一个写者写的同时可以有多个读者。不是允许多个写者同时写。
- `synchronous=FULL`：每次提交都确保落盘，慢一点但更不容易丢数据。

Hikaro 用同步的 SQLite API，但放在一个 **Worker 线程**里跑；主线程通过带 id 的消息请求它，用 pending Map 找回对应的 Promise（和 Versta 的 JSON-RPC 一个思路）。这样同步的数据库操作不会卡住界面。

## 6.6 恢复会话，不是重放操作

“把配置从 A 改成 B”，崩溃可能发生在两个位置：

| 崩溃时刻 | 文件 | 数据库 |
| --- | --- | --- |
| 写文件之前 | A | 有调用，没结果 |
| 写文件之后、结果入库之前 | B | 有调用，没结果 |

**数据库看起来一模一样，现场却不同。** 缺结果只能说明“没找到结果记录”，不能说明“没执行”。所以重启后不能自动重放工具调用：改文件也许重放无害，但追加日志、发外部请求就会重复。

Hikaro 在 `run()` 开头扫一遍历史，把“有调用、没结果”的补上一条错误结果：

```ts
// 源码：packages/core/src/index.ts（run 开头）
const unresolved = new Map<string, { name: string }>();
for (const m of prior) {
  for (const c of m.toolCalls ?? []) unresolved.set(c.id, { name: c.name });
  if (m.callId) unresolved.delete(m.callId);
}
for (const [callId, call] of unresolved)
  await this.message({
    role: "tool", name: call.name, callId,
    text: "Interrupted operation. Its outcome is unknown. Inspect current state before retrying; do not replay automatically.",
    isError: true, timestamp: Date.now(),
  });
```

用 `callId` 而不是工具名配对：同一个 `edit_file` 可能调用了好几次，只有其中一次缺结果。

补上的结果告诉模型“结果未知，先检查现场再说”。这样“不知道”变成一个具体的下一步：先只读地检查文件现在的内容。

## 6.7 旧进程复活：租约的 epoch

进程卡住很久（比如电脑休眠），租约过期，别的进程接手了会话。旧进程醒来想继续写事件，怎么办？

Hikaro 的租约记录 `owner`、`epoch`、过期时间。每次有人重新拿到租约，`epoch` 加一。写入时数据库同时核对三者，旧进程的 epoch 对不上，写入被拒绝。

但数据库拒绝旧事件，不等于撤销了旧进程在别处做过的事（比如它醒来那一瞬间已经改了文件）。

恢复时分三个问题问：

1. **记录**：数据库里有哪些事实？
2. **执行**：旧的模型请求、子进程还在跑吗？
3. **现场**：文件和外部系统现在是什么状态？

重新打开一个会话只解决第 1 个。
