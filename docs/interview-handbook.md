# Hikaro 面试手册

更新时间：2026-10-13。内容依据当前代码。口述回答可直接使用；个人贡献请按实际负责范围调整。

## 一分钟项目介绍

> Hikaro 是一个 TypeScript 本地 AI 编程助手，当前主线是独立 Agent 核心、全屏 TUI 和 Pi 双向集成。用户提出任务后，模型调用文件、搜索、终端和 Git 工具，完成连续操作。项目复用 pi-ai 接入模型，但原生 Agent 循环由项目自己实现。主要工程工作是控制工具权限、保存和恢复会话，以及在长会话中管理上下文。核心机制已经实现，真实账号、日常使用和 Pi 异常路径仍有验收工作。

## 1. Agent 循环

### Q1：Agent 和普通聊天接口有什么区别？

**口述回答：**

> 普通聊天主要返回文本。Agent 会把模型返回的工具调用转换成实际操作，再把结果传回模型。Hikaro 每轮读取历史、请求模型、执行工具、保存结果，然后进入下一轮。模型没有返回工具调用且没有待处理补充指令时，这次执行结束。

**追问补充：** 模型认为任务结束，不等于任务经过验证。验证是否完成，要看实际工具结果；执行核心没有通用的业务成功判定器。

### Q2：为什么自己实现循环？Pi 提供了什么？

**口述回答：**

> 项目需要自己控制工具权限、取消、事件记录和预算，所以把执行循环放在 core。pi-ai 负责模型接入，pi-tui 提供终端界面基础。这样可以复用底层能力，同时保留执行行为的控制权。另一个可选模式通过 RPC 调用外部 Pi，那条路径由 Pi 负责执行和权限。

### Q3：一轮任务具体按什么顺序执行？

**口述回答：**

> 先获取会话租约，检查历史中没有结果的工具调用，再保存新请求。每轮检查取消和预算，整理上下文，然后请求模型。流式文本用于展示，完整模型消息保存后才执行工具。每个工具结果都写入历史，下一轮模型根据这些结果继续判断。

**关键顺序：** 保存模型工具调用 → 执行工具 → 保存工具结果。这个顺序让中断后可以发现缺失的结果，但无法把数据库记录和外部副作用做成同一个事务。

### Q4：同一轮多个工具会并行执行吗？

**口述回答：**

> 当前原生循环按模型返回的顺序串行执行工具。这样便于控制文件和命令之间的依赖。代价是独立操作不能在这个循环里同时执行。项目另有子 Agent 编排能力，但它与单轮工具并行是两个概念。

### Q5：如何防止无限循环和费用失控？

**口述回答：**

> 核心同时限制轮次、模型调用次数和费用。Agent 默认最多执行 32 轮，默认共享预算是 128 次模型调用和费用上限 10，配置可以覆盖。每轮请求前检查预算，用量在模型完成后累计。因此费用上限是请求边界上的控制，单次请求仍可能把累计费用推过上限。

### Q6：模型给出错误参数或工具失败怎么办？

**口述回答：**

> 所有工具通过统一入口调用，先用 Zod 校验参数。工具不存在、参数错误或执行异常，会转换成错误结果。循环把错误结果传回模型，让模型决定下一步。当前没有通用自动重试策略，因为文件修改和命令可能已经产生副作用。

**追问补充：** Provider 没有返回完整消息、上下文超预算或循环达到上限，会让本次执行失败，不能把这些情况当作正常完成。

### Q7：取消怎么实现？能保证马上停止吗？

**口述回答：**

> 核心使用 AbortController，把取消信号传给模型和工具。取消时还会清理排队请求和补充指令。工具执行前会检查信号，具体工具也需要响应取消。这是协作式取消，不能承诺所有操作立即停止，也不能撤销已经发生的文件修改或外部副作用。

### Q8：为什么流式展示和完整消息分开？

**口述回答：**

> 文本增量让用户及时看到进度，完整消息才是下一轮模型使用的历史。核心把文本和推理增量按约 24 毫秒间隔合并发送，流结束后刷新剩余内容。这样可以减少事件和界面刷新次数。工具调用要等完整模型消息保存后才开始执行。

### Q9：执行中收到新输入怎么办？

**口述回答：**

> 普通请求进入队列，由同一个 Agent 顺序处理。补充指令进入另一条队列，在下一轮模型请求前加入历史。普通请求队列上限是 32，补充指令队列上限是 16。这避免同一 Agent 同时运行两个循环，也让追加指令有明确的生效边界。

## 2. 会话恢复

### Q10：为什么保存事件，而不是只保存聊天文本？

**口述回答：**

> 聊天文本不能完整描述执行过程。项目还保存任务开始和结束、工具开始和结束、文本增量等有序事件。消息历史也是事件的一部分。这样既能读取对话，也能追踪执行状态。存储事件支持状态重建，但不意味着可以安全重放工具。

### Q11：SQLite、WAL 和 Worker 分别解决什么问题？

**口述回答：**

> SQLite 适合本地应用，不需要额外数据库服务。WAL 改善读写共存，项目还使用 synchronous=FULL 控制提交持久性。数据库运行在 Worker，主线程通过请求 ID 等待结果，避免同步 SQL 直接阻塞终端交互。不过数据库操作仍有成本，Worker 也不意味着写入无限并行。

### Q12：恢复会话和恢复执行有什么区别？

**口述回答：**

> 恢复会话是读取历史、模型设置和当前状态。恢复执行意味着继续产生副作用，风险更高。Hikaro 默认恢复当前工作区上次打开的会话，但不会自动重放任务。用户再次发起任务时，核心先检查缺失的工具结果，再开始新一轮执行。

### Q13：命令执行成功，但保存结果前崩溃怎么办？

**口述回答：**

> 这是最关键的恢复难点。历史里有工具调用，却没有对应结果，无法判断命令有没有成功。核心会补一条错误结果，明确说明操作中断、结果未知，并要求检查当前状态。不会直接重试，因为重试可能重复修改文件或重复执行命令。

**例子：** 创建文件后崩溃，恢复时先检查文件和内容；不能仅凭缺少工具结果判断创建失败。

### Q14：为什么不能保证 exactly-once？

**口述回答：**

> SQLite 事务可以约束数据库写入，但文件操作、Shell 命令和外部服务不在这个事务里。操作已经成功、结果还没保存时，仍然会出现不确定窗口。当前通过命令去重、会话租约和禁止自动重放降低重复执行风险，但不承诺任意工具 exactly-once。要进一步实现，需要工具自身支持幂等键或可核查的操作记录。

### Q15：两个进程同时打开一个会话怎么办？

**口述回答：**

> 执行前通过 SQLite 条件更新获取会话租约。租约记录 owner 和过期时间，默认有效期 30 秒，每 10 秒续租。另一个 owner 在租约有效时不能获取执行权。正常结束时按 owner 释放，续租失败则取消当前执行。

**追问补充：** 租约不是所有外部副作用的强锁。旧进程长时间停顿、租约过期后仍可能恢复；当前没有对所有工具实施 fencing token，也不能强制撤回已发出的操作。

### Q16：断线后如何避免丢事件或重复提交？

**口述回答：**

> 协议提供带游标的快照和后续事件读取接口，独立客户端可以根据事件序号衔接。当前共享状态层区分持久事件序号与 scope revision，发现通知缺口会要求新快照。RPC 命令使用稳定 ID，数据库通过唯一记录去重。这解决状态同步和重复提交的问题，但命令去重不等于工具副作用只发生一次，也不等于失败命令会自动重新执行。

### Q17：历史很大时，恢复会不会慢？

**口述回答：**

> 界面按游标分页读取历史，不会一次加载全部消息。模型循环读取近期历史时，也有最多 1000 条消息和约 8 MiB 的累计读取边界，再做上下文裁剪。大工具结果保存为文件，消息保留有限预览。这些限制控制单次加载，但不代表整个数据库的大小被限制。

### Q18：分支和压缩有什么不同？

**口述回答：**

> 分支会新建会话，并复制原会话的消息事件，保留父会话关系。压缩先生成摘要，再新建只有续接摘要的子会话。两者都保留原会话，但不会复制或回滚工作区文件。所以对话分支不是 Git 分支，也不是文件检查点。

## 3. 上下文压缩

### Q19：上下文管理具体分哪几层？

**口述回答：**

> 有三层边界。存储层限制单次读取，界面层限制可见历史，模型层限制发送的上下文。模型上下文不够时，先裁剪旧轮次；用户调用 compact 时，再把历史生成续接摘要。持久化历史仍然保留，不会因为模型上下文裁剪而删除。

### Q20：为什么按用户轮次裁剪？

**口述回答：**

> 工具调用和工具结果有对应关系，按字符随意截断容易拆开它们。当前从历史开头移除完整用户轮次，保留较新的完整轮次。如果当前轮次本身超预算，系统会报错，要求分支或压缩，不继续把当前轮次切碎。这个策略依赖历史本身完整，存储读取边界仍可能让最早一段历史不完整。

### Q21：当前 token 预算怎么算？准确吗？

**口述回答：**

> 当前不是精确 token 计算。代码用消息序列化后的 UTF-8 字节数估算，每张图片加 8192 的固定估算值，预算取 contextWindow 数值的 60%，最低 1024。它是工程上的保守启发式，不能保证实际请求一定不超模型限制。system、工具定义和输出预留还需要更完整的预算处理。

**不要说：** “已经精确计算 token”或“60% 是严格安全上限”。

### Q22：旧历史被省略后，模型会不会编造？

**口述回答：**

> 系统会发出上下文省略事件，并在模型消息中说明旧内容已被省略，要求不要假设其内容，必要时询问缺失约束。这能降低误用历史的风险，但不能保证模型完全遵守。因此关键约束的稳定保留仍然是后续要加强的部分。

### Q23：compact 怎么处理整段历史？

**口述回答：**

> compact 每次读取 40 条消息，再把文本切成有界批次。每一批都让模型合并“上一份摘要”和“新历史”，逐步得到最终摘要。提示要求保留目标、约束、决策、路径、操作、测试结果、未完成工作和不确定性。成功后创建续接子会话，写入摘要和来源关系，原会话继续保留。

**实现细节：** 批次字符目标是 contextWindow 数值的 30%，摘要字符目标是 20%，两者最低 512。这仍是字符启发式，不是精确 token 预算。

### Q24：摘要不准确怎么办？

**口述回答：**

> 摘要是有损表示，重复合并可能积累遗漏或误解。当前用明确的保留要求约束模型，并保留原会话作为核查依据。摘要为空会失败；超过目标长度两倍也会失败。但项目没有自动证明摘要语义完整，遇到关键事实仍应回查原记录。

### Q25：压缩时会完整保留图片和工具调用结构吗？

**口述回答：**

> 当前压缩主要把角色、名称和消息文本转成摘要输入，没有完整保留图片内容和结构化工具参数。因此它适合文本续接，不能承诺无损保存所有多模态和工具细节。原始记录仍然保留，但续接摘要不一定包含这些信息。

### Q26：压缩失败会破坏原会话吗？压缩期间能继续输入吗？

**口述回答：**

> 压缩要求当前 Agent 空闲，并获取会话租约。压缩期间普通请求会被拒绝，避免历史同时变化。摘要成功后才创建续接会话，因此模型摘要失败不会覆盖原历史。不过子会话创建和后续摘要、来源事件写入不是一个总事务，中途存储失败仍可能留下不完整子会话。

### Q27：为什么不直接用向量检索替代压缩？

**口述回答：**

> 检索适合找相关片段，摘要适合保留任务的连续状态。检索可能漏掉约束或尚未完成的步骤，摘要也可能遗漏细节，所以两者可以互补。项目有可选索引模块，但当前主线没有把它做成自动会话记忆，不能说已经实现完整长期记忆系统。

### Q28：下一步怎么改进上下文管理？

**口述回答：**

> 我会先完善预算，把 system、工具定义、图片和输出预留纳入估算，并尽可能使用对应模型的 tokenizer。再把关键约束和未完成任务做成稳定结构，减少滚动摘要丢失。最后增加带来源的摘要核查和自动压缩触发。这些属于改进方向，不能当作当前已实现能力。

## 4. 技术亮点和难点的短回答

### 技术亮点：约 30 秒

> 主要有三个亮点。第一，自研 Agent 循环，统一管理工具执行、取消和预算。第二，用有序事件和 SQLite Worker 保存执行过程，支持分页读取和会话恢复。第三，通过权限策略和有界输出控制本地操作与资源使用。界面、模型接入和执行核心分开，方便后续替换和扩展。

### 最大难点：约 30 秒

> 最大难点是中断后的不确定性。工具可能已经执行成功，但结果没有保存，所以恢复时不能直接重试。项目通过缺失结果检查、会话租约和禁止自动重放控制风险。另一个难点是长会话：要缩小上下文，又要保留约束和工具关系，所以采用完整轮次裁剪、分批摘要和原历史保留。

### 设计取舍：约 20 秒

> 项目优先让执行边界清楚。当前工具串行执行，错误交给模型处理，中断任务不自动重放。上下文采用启发式预算和显式压缩。这些选择降低了实现复杂度，但工具并行、精确预算和自动压缩仍有改进空间。

## 5. 面试前速记

| 概念 | 一句话 | 不要夸大的边界 |
| --- | --- | --- |
| Agent 循环 | 模型提出调用，核心执行，结果回传后继续。 | 模型结束不等于任务已验证。 |
| 取消 | AbortSignal 传给模型和工具。 | 不保证立即停止，也不回滚副作用。 |
| 会话恢复 | 恢复历史和设置，检查结果未知的调用。 | 不自动重放，不承诺 exactly-once。 |
| 会话租约 | 30 秒有效，每 10 秒续租。 | 没有覆盖所有副作用的 fencing。 |
| 历史裁剪 | 按完整用户轮次保留较新上下文。 | 当前是字节估算，读取边界也可能丢掉旧内容。 |
| compact | 分批合并摘要，生成续接子会话。 | 有损压缩，未完整保留多模态和工具结构。 |
| fork | 复制消息历史，建立子会话。 | 不创建 Git 分支，不回滚文件。 |
| 当前范围 | 独立核心、TUI、Pi 双向集成。 | 共享协议与远程适配已有实现；原生手机客户端与跨端真实使用仍待验收。 |

## 6. 代码依据

- `packages/core/src/index.ts`：请求队列、执行循环、工具入口、取消、预算和租约续期。
- `packages/core/src/context.ts`：上下文裁剪和分页滚动摘要。
- `packages/storage/src/index.ts`：数据库 Worker 请求封装。
- `packages/storage/src/worker.mjs`：WAL、事件、分页、分支、租约和命令去重。
- `packages/runtime/src/index.ts`：创建续接子会话。
- `apps/cli/src/rpc.ts`、`packages/protocol/src/index.ts`：RPC、快照游标与事件读取接口。
- `README.md`、`TODO.md`：当前范围与未完成验收事项。
