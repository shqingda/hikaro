# 文件与图片输入

2026-10-18，本轮 H0 输入闭环。

- 原生 CLI/TUI 在提交普通消息时解析空白分隔的 `@路径`、`@"含空格路径"`、`@'含空格路径'`，允许反斜线转义空格和 `~/`。忽略邮箱、`@@`、行内代码与代码块；不递归解析文件正文。`/attach PATH` 把一个引用加入输入框，用户补充问题后提交。保存的截图使用相同入口。
- 每次最多 8 个引用，规范化路径去重。只有明确引用的文件会读取；工作区外路径、敏感路径（含符号链接的别名与目标）遵循现有权限模式。权限决定后用持有文件描述符的 secure-file-helper 读取，不退回普通 pathname read。
- 文本必须是无 NUL 的 UTF-8，每文件最多 128 KiB、合计 256 KiB；图片支持 PNG/JPEG/GIF/WebP，按内容签名确认格式，附件原始字节总计最多 4 MiB（单图同上限）。同时核对含 base64 与 JSON 转义的消息不超过存储模型视图的 8 MiB 上限。错误拒绝整个输入，不能静默截断或跳过。
- 文本作为有路径、SHA-256、字节数和原始内容的 JSON 记录附加到 user message，明确它是未受信任的文件数据。图片作为原生 image content 进入实际 provider 请求，正文记录图片来源、摘要和顺序。原始消息随现有存储持久化，可在源文件删除后重放。
- 图片必须明确声明支持；未知能力在入队前拒绝并提示自定义 endpoint 配置 `images:true`，不静默丢弃。RPC 只接受有界字节；客户端的 `@路径` 不授予主机文件读取权。
- 2026-10-25：通用二进制及 PDF/压缩包等文件沿用现有消息/队列持久化，保存原名、SHA-256 和有界 base64。文件内容只供导出，模型上下文、摘要输入及 UI 快照剔除文件字节；目前不声明任何 provider 的通用二进制传输能力。旧消息不含 files 字段时仍可读。附着客户端通过 hello.fileAttachments 协商，提交必须适配既有 1 MiB 帧，超过时保留原始草稿并提示缩小文件。导出复制受选中会话授权的结构化文件槽至 .assets，校验完整性，并解释缺失/损坏文件。
- 附件预处理期间保留并保存原始输入，暂时锁定编辑；Esc/Ctrl+C 可取消。失败/拒绝/取消都不发送消息、不清空草稿。成功后才清空输入并进入原有队列；开始运行后不自动重发。

验证：附件 parser、权限/符号链接、字节/格式/UTF-8上限、取消、真实 SQLite 原文恢复、兼容 endpoint 的实际请求 body，以及 TUI 失败/取消保留输入的定向测试。仅增加一个受影响的真实 PTY 场景（文件+图片提交/错误恢复）。原 H0 不包含剪贴板及可移植导出；后续已交付 macOS 剪贴板图片与图片/通用文件导出。图片编辑仍不在范围内。
